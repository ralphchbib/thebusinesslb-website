# Phase 6B — Risk Assessment

Risks specific to turning the Page Builder into a Landing Page Factory — i.e., risks that come from **scale and non-developer authorship**, not risks already retired by Phase 6A (those are noted as closed where relevant).

## Technical risks

| Risk | Severity | Assessment |
|---|---|---|
| Reserved-slug collisions at higher page-creation velocity | Medium | `lib/cms/reserved-slugs.ts` is a manually-maintained `Set` with no automated route-tree check — already a known gap (Architecture Review §5). More editors creating more landing pages, faster, raises the odds someone picks a slug that collides with a literal route, though the 3-layer defense (validate + reject-before-query + hard-fail-build) means a collision is loud and blocking, not silent. **Mitigation**: no schema change needed; add a lint/CI check that diffs `app/(app)/*` route segments against `RESERVED_SLUGS` — flagged as a good candidate for a small follow-up, not a Phase 6B blocker. |
| Fragmenting into per-type collections instead of extending the existing `pageType` field | Medium | A tempting-but-wrong design would be to create `service-landing-pages`, `location-pages` etc. as separate Payload collections to "keep things organized." This would duplicate access control, preview wiring, revalidation hooks, and reserved-slug validation six times over, for a problem the existing generic Pages+`pageType` model already solves. **Mitigation**: explicitly decided against in the SEO Strategy §3 — extend `pageType`, don't fragment collections. |
| Block-count growth degrading Payload admin performance/usability | Low | Going from 8 to ~14 block types is well within normal Payload usage patterns; the `blocks` field's block-picker UI scales fine to this count. Not a real risk at this scale. |
| Comparison Table / Pricing block authoring errors (misaligned rows/columns) | Low-Medium | Addressed directly in the Block Gap Analysis by deliberately constraining the Comparison Table to a fixed 2-column design rather than a generic N-column table — removes the alignment-drift failure mode by construction. |
| Rich text remains structurally unavailable | Low (accepted, not a regression) | Already true since Phase 6A; not a new risk introduced by 6B, but worth restating: any new "flexible text" block must continue the structured-array pattern, not attempt `richtext-lexical` again without a fresh, live compatibility spike against whatever Payload/Node versions are current at implementation time. |
| Standalone-script revalidation gaps during validation | Low (known, accepted) | The same `[cms:revalidate:error] static generation store missing` limitation seen in every prior phase's validation work (scripts run outside a live request context) will recur during Phase 6B's own validation. Already a well-understood, disclosed, non-blocking pattern — not a new risk, just worth budgeting for in the Validation Plan. |

## SEO risks

| Risk | Severity | Assessment |
|---|---|---|
| Duplicate/near-duplicate content across templated location or industry variants | **High** — the single largest risk this phase introduces | Covered in depth in the SEO Strategy §2. A factory that makes it *easy* to spin up "Website Design Beirut," "Website Design Tripoli," "Website Design Jounieh" from the same block skeleton makes it equally easy to accidentally produce search-engine-visible duplicate content, which can suppress rankings for all variants rather than helping any one. **This is fundamentally an editorial-process risk, not something the schema can prevent** — the strongest available mitigation is the Content Operations checklist requiring genuinely distinct copy per variant, plus defaulting thin/short-lived page types to `noindex`. |
| Crawl-budget dilution from an unbounded number of low-value pages | Medium | More indexed pages is not automatically better; a large number of thin campaign/seasonal pages can dilute crawl budget and signal lower average content quality sitewide. **Mitigation**: the `noindex`-by-default-for-campaign/seasonal recommendation (SEO Strategy §2) plus the quarterly unpublish-review process (SEO Strategy §6). |
| Missed `serviceSchema()`/structured-data wiring for new page types | Low | Currently Pages only emits `breadcrumbSchema`+conditional `faqSchema` — already identified and scoped as a fix in the SEO Strategy §4, not a residual risk once implemented. |
| Sitemap growing without corresponding lastModified accuracy | Low | `sitemap.ts` currently sets `lastModified: now` (build/request time) for every entry uniformly, not the Page's actual last-edited timestamp — already true today, not a new Phase 6B regression, though it becomes slightly more noticeable at higher page volume since it means the sitemap can't signal genuinely fresh vs. stale content to crawlers. Worth a note for a future pass; not a Phase 6B blocker since fixing it is unrelated to the Landing Page Factory feature itself. |

## Editorial risks

| Risk | Severity | Assessment |
|---|---|---|
| Non-developer editors publishing incomplete or low-quality pages | Medium-High | This is the core trade-off of "without developer involvement" — the schema enforces required fields (`seoTitle`, `seoDescription`, `minRows: 1` on blocks) but cannot enforce copy *quality*, brand voice consistency, or genuine differentiation between similar pages. **Mitigation**: a lightweight editorial checklist/review step before publish (part of Content Operations), and leaning on the existing draft→preview→publish workflow so nothing goes live unreviewed — this workflow already exists and needs no new code, only a process convention that editors are expected to use Preview before Publish. |
| Brand/voice drift across many editor-authored pages | Medium | More authors (or more volume from the same author, faster) raises the chance of tone inconsistency. Not solvable in code; addressed via a short editorial style-guide reference as part of Content Operations, out of scope for engineering. |
| Slug/naming inconsistency (e.g., `website-design-lebanon` vs `web-design-lebanon` vs `websites-lebanon` for near-identical intent) | Medium | Left unaddressed, this fragments SEO authority across near-duplicate URLs rather than consolidating it on one strong page. **Mitigation**: a documented slug/naming convention per landing-page category as part of Content Operations (e.g., `{service}-{location}` lowercase-hyphenated) — a process convention, not a technical constraint, since Payload's `slug` field is free text by design (matches every other collection). |
| No workflow-level ownership/approval gate beyond Editor/Admin roles | Low | The existing 2-role model (`admin`/`editor`, `payload/collections/Users.ts`) has no "pending review" state beyond Payload's own draft/published binary — an Editor can publish directly with no Admin sign-off required. This is a pre-existing characteristic of the whole CMS, not something Phase 6B changes; flagged for awareness only, since higher publishing velocity means this gap is exercised more often. Out of scope to change unless the business explicitly wants an approval workflow. |

## Performance risks

| Risk | Severity | Assessment |
|---|---|---|
| Additional blocks increasing per-page render/query cost | Low | Every new relationship-backed block (Pricing if it goes the relationship route, Logo Cloud if it later gains a Testimonials-pull) adds one more `getXByIds()`-style query per page render, same pattern as `FaqPageBlock`/`ServicesGridBlock` today — these already run in parallel via `Promise.all` where multiple resolvers are needed on one page, and Pages are statically generated (`generateStaticParams`) with on-demand revalidation, so render cost is paid once per content change, not per visitor. Not a meaningful concern at the page counts under discussion (dozens, not thousands). |
| Media-heavy landing pages (Logo Cloud + Hero background + Stats icons, etc. on one page) slowing image-heavy pages | Low-Medium | All existing image fields already go through Next Image optimization and the existing size presets; a landing page stacking many image-bearing blocks increases total page weight but each image is independently optimized/lazy-loadable. Worth a Lighthouse/perf check in the Validation Plan for a "maximal" test page (many blocks, many images) specifically, rather than assuming it's fine. |
| Sitemap/build time growth at higher Page volume | Low | `getPublishedPageSlugs()` currently caps `limit: 100` — **this is a real, currently-latent ceiling** worth flagging: if the Landing Page Factory succeeds and the business genuinely creates 100+ Pages, this limit will silently truncate the sitemap and `generateStaticParams` rather than error. Not urgent at current volume, but should be tracked as a known ceiling, not forgotten. |

## Content quality risks

| Risk | Severity | Assessment |
|---|---|---|
| Thin, templated pages perceived as low-value by users (not just search engines) | Medium | Same root cause as the SEO duplicate-content risk (§ above) but from a user-trust angle — a visitor who's seen "Website Design Beirut" and clicks through to "Website Design Tripoli" and finds identical copy with one word changed loses trust in the brand. Mitigation is identical: genuine per-variant differentiation, enforced editorially not technically. |
| Accessibility regressions from new blocks authored without review | Low-Medium | New presentational components (Stats, Logo Cloud, Feature Grid, Pricing, Process, Comparison Table) each need the same accessibility bar as existing blocks (semantic headings, alt text via the already-required Media `alt` field, sufficient color contrast, keyboard-navigable if interactive). Addressed as an explicit checklist item in the Validation Plan rather than assumed. |
| No content-freshness signal for editors ("this campaign page is 8 months old and still live") | Low-Medium | Directly addressed by the quarterly unpublish-review process recommended in the SEO Strategy §6 — currently no code-level staleness indicator exists (Pages has no "campaign end date" field). A `campaignEndDate` optional field with an admin-list column flag is a plausible small addition if this becomes a recurring pain point — not required for MVP, noted as a fast-follow candidate. |

## Overall risk posture

**Medium.** No risk identified here blocks a GO decision — every technical risk has a known, low-effort mitigation already used elsewhere in this codebase, and every high-severity item (duplicate content, editorial quality) is fundamentally a *process* risk that engineering can support (defaults, checklists, `noindex` gates) but cannot fully solve in code. The Final Recommendation should make explicit that Phase 6B's success depends as much on the Content Operations workflow being actually followed as on the blocks themselves being built correctly.
