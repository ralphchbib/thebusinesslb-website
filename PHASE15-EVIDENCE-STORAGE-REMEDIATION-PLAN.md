# Phase 15 — Evidence Storage Remediation Plan

Addresses the critical finding in `PHASE15-PRODUCTION-DEPLOYMENT-REPORT.md` §D: verification evidence uploads fail with an HTTP 500 in production, every time, reproducibly. This plan documents root cause and design before any fix is written.

---

## 1. Root Cause

`VerificationEvidence` (`payload/collections/VerificationEvidence.ts`) is configured with Payload's built-in local-disk upload adapter (`upload: { staticDir: "verification-evidence-uploads", mimeTypes: [...] }`), deliberately kept off the `vercelBlobStorage` plugin registered in `payload.config.ts` — a decision made for a real, correct reason: that plugin (as configured for `Media`) only supports **public** blob access, and registering evidence with it would have made submitted documents fetchable by anyone with the URL, defeating the phase's entire purpose.

Local-disk storage means every upload attempt calls Node's `fs.writeFile` (via Payload's own upload-handling pipeline) against a path resolved relative to the deployed application bundle. On Vercel's production serverless runtime, the deployed bundle's filesystem is **read-only** — the only writable location is `/tmp`, which is ephemeral per-invocation and not where `staticDir` resolves to. The write throws, Payload's REST layer catches it and returns a generic `500 "Something went wrong."` (the specific underlying error is suppressed in production by design, since `debug` is off).

## 2. Why Local-Disk Storage Works Locally But Fails on Vercel

Locally (`next dev` / `next start` on a developer machine), the deployed "bundle" is just the project directory on a normal, writable filesystem — `fs.writeFile` to `verification-evidence-uploads/` succeeds trivially, and every dev/staging validation pass in this phase (implementation, both release reviews, remediation) ran exactly this way, which is why the defect was never caught before this was actually deployed and exercised against real Vercel infrastructure. This is not a difference in Payload's behavior — it is a difference in what the underlying filesystem allows, and it was already disclosed as a known trade-off in every prior report (`PHASE15-IMPLEMENTATION-REPORT.md` §C: *"local-disk storage does not persist across Vercel's ephemeral serverless filesystem in production"*). What none of those passes could confirm — because none of them had run against real production infrastructure yet — is that the actual failure mode is an immediate write error, not a slower persistence problem. `PHASE15-PRODUCTION-DEPLOYMENT-REPORT.md` §D closes that gap: it is a hard, reproducible failure, isolated by confirming the request correctly reaches Payload's upload-handling code (a fileless request correctly returns `400 "No files were uploaded."`) and fails only at the point a real file is written (`500`).

## 3. Privacy Requirements

Restated from the phase's own critical requirement, unchanged by this remediation:

- No public URL for any evidence file, ever — not "hard to guess," genuinely inaccessible without passing Payload's own access control.
- Read access limited to: the uploading account (their own evidence only), and verification staff (`admin`/`verification-officer`) — never `moderator`, never another network account, never `anyone`.
- This is already correctly implemented at the Payload access-control layer (`readOwnEvidenceOrVerificationStaff`, `payload/access-verification.ts`) and was independently verified against production in the deployment-report pass (anonymous/moderator/other-account all correctly blocked; officer/admin correctly allowed). **This remediation must not touch that access-control logic at all** — the bug is entirely in the storage layer beneath it, and the fix must be provable as storage-layer-only, so none of the already-reviewed and already-production-verified access-control behavior is put back at risk.

## 4. Storage Requirements

What the replacement storage layer must provide, derived directly from the objective:

1. **Uploads succeed in production** — no dependency on a writable local filesystem.
2. **Files persist** — surviving across serverless invocations and cold starts, unlike local disk.
3. **Reads are access-controlled at request time**, not just at rest — knowing a file's storage location/URL must not be sufficient to fetch it; Payload's own collection access control must be evaluated on every read, exactly as it already is for the local-disk adapter's static route today.
4. **No public URL is ever generated or returned** to any client, authorized or not — the storage backend's own object identifier should never be handed to the browser directly.
5. Reuses infrastructure and credentials already provisioned for this project wherever possible, to minimize new operational surface (new secrets, new services, new failure modes) for what is a privacy-critical, low-volume upload path.

## 5. Migration Strategy

**Recommended: a custom, private-access Vercel Blob storage adapter**, using the `@vercel/blob` SDK directly rather than the `@payloadcms/storage-vercel-blob` plugin.

### Why this option, evaluated against the alternatives named in the objective

| Option | Meets requirements? | Cost to adopt |
|---|---|---|
| **Private Vercel Blob (recommended)** | Yes — `@vercel/blob@2.3.1` (already installed, as a transitive dependency of the existing `@payloadcms/storage-vercel-blob` package) natively supports `access: 'private'`: `put()` accepts it, and reading content back requires the same server-side `BLOB_READ_WRITE_TOKEN` this project already has provisioned in production (confirmed via `vercel env ls production`) — a private blob's URL alone does not serve content to an unauthenticated request. | **Lowest.** No new credentials, no new service, no new dependency to add (only needs `@vercel/blob` promoted from a transitive to a direct `package.json` dependency, pinned to the already-installed version). |
| S3-compatible private bucket (AWS S3 / Cloudflare R2 / etc.) | Yes, in principle — this is the conventional, well-proven shape for exactly this problem (private bucket, server-mediated or short-lived signed reads). | **Highest.** Requires provisioning a new bucket and access/secret credentials outside this session's reach (the user would need to create these in a third-party console), adding a new SDK dependency (`@aws-sdk/client-s3` or equivalent), and adding new Vercel environment variables before any of it could be deployed or tested. |
| Supabase Storage private buckets | Plausible — this project already depends on Supabase for Postgres, so there is some infrastructure affinity. | **High.** No evidence Storage is enabled on this project's Supabase instance today; would need a Supabase URL + service-role key (not present in `.env.local` or Vercel's env list) and a new client dependency (`@supabase/supabase-js`), none of which can be provisioned or confirmed from this session. |

The deciding factor is not correctness — all three can satisfy the storage requirements in §4 — it is that the Vercel Blob option is the only one **deployable and testable immediately**, using credentials and infrastructure that already exist in this exact production environment, with no dependency on the user going to provision something in a separate console first. If it turns out — only discoverable by actually deploying and testing against real production, per this project's established validation discipline — that private-blob access is unavailable on this project's Vercel plan (see Risk Assessment §6), the S3 or Supabase Storage path remains available as a fallback, with the evaluation above already done.

**Why not the official `@payloadcms/storage-vercel-blob` plugin, even for private access:** inspecting the installed version (3.87.0) directly shows it does not yet support this. Its own type definition states outright: *"Access control level. Currently, only 'public' is supported. Vercel plans on adding support for private blobs in the future."* Its `baseUrl` construction (`https://${storeId}.${access}.blob.vercel-storage.com`) is hardcoded around the public-blob URL pattern. And its static-file read handler (`getFile.js`) calls the SDK's authenticated `head()` for metadata but then fetches the actual file bytes with a **plain, unauthenticated `fetch()`** — which is correct for a public blob (no auth is needed) but would not correctly retrieve a private blob's content, since Vercel's private-blob storage requires the token on every read, not just for metadata. Forcing `access: 'private'` through this plugin would therefore plausibly upload correctly but fail to ever serve the file back — a different, but equally broken, outcome. This is why the fix is a small custom adapter, not a configuration change to the existing plugin.

### Implementation shape

1. **Add `@vercel/blob` as a direct dependency** in `package.json`, pinned to `2.3.1` (already resolved and installed today as a transitive dependency — this makes that dependency explicit and stable against future `npm install`s, rather than relying on hoisting).
2. **Write a small custom storage adapter** (a new file, e.g. `payload/verification-evidence-blob-adapter.ts`) implementing the four-function interface `@payloadcms/plugin-cloud-storage` expects (`handleUpload`, `handleDelete`, `generateURL`, `staticHandler`) — the same interface the official Vercel adapter already implements, used here as a direct reference:
   - `handleUpload`: calls `@vercel/blob`'s `put(key, buffer, { access: "private", token, addRandomSuffix: true, ... })` directly, returning the resulting filename for Payload to persist on the document.
   - `handleDelete`: calls `del(url, { token })`.
   - `generateURL`: returns a stable, internal-only identifier (not exposed to the client as a fetchable URL) — Payload requires a `url` field to be populated on the document, but nothing about this remediation depends on that value ever being dereferenced directly by a browser.
   - `staticHandler`: given a filename, calls the SDK's own **authenticated** `get(key, { access: "private", token })` — not a raw `fetch()` — and streams the returned content back as the `Response`. This is the exact point the official plugin's equivalent function is incomplete for private blobs, fixed here by using the SDK function actually documented for reading private blob content.
3. **Register this adapter directly via `cloudStoragePlugin` from `@payloadcms/plugin-cloud-storage`** (the lower-level function the `vercelBlobStorage()` wrapper itself calls), scoped to only the `verification-evidence` collection — leaving `Media`'s existing, working, public-blob `vercelBlobStorage()` registration completely untouched.
4. **Change `VerificationEvidence.upload`** from `{ staticDir, mimeTypes }` to `{ disableLocalStorage: true, mimeTypes: [...] }` — telling Payload not to attempt any local-disk write at all now that a cloud adapter handles storage.
5. **Do not touch `access-verification.ts`, `readOwnEvidenceOrVerificationStaff`, or any access-control code.** Payload's own `plugin-cloud-storage` route wrapper already gates the custom `staticHandler` behind the collection's own `access.read` function before ever invoking it (confirmed by direct inspection of `node_modules/@payloadcms/plugin-cloud-storage/dist/plugin.js`) — this is the exact same mechanism that already made local-disk storage's static route correctly return `403` for anonymous/cross-account/moderator requests, and it applies identically regardless of which adapter is registered. This remediation is provably storage-layer-only.

## 6. Risk Assessment

- **Primary risk: private-blob write access may not be available on this project's Vercel Blob plan/tier.** This could not be pre-verified from this session — `vercel env pull` returns Vercel-managed secrets as a redacted `[SENSITIVE]` placeholder rather than the real token value, so the private-access `put()` call could not be tested against real credentials before deployment. **Mitigation:** the very first thing the post-implementation validation does is a real upload attempt against production; if it fails with an access/plan-related error (as opposed to succeeding), this plan's own comparison table already names the fallback (S3-compatible private bucket, or Supabase Storage) and what each would require the user to provision. This is not a silent risk — it is disclosed here and will be resolved, one way or the other, by the validation step itself, not assumed away.
- **Legacy evidence rows**: none exist — the production sweep in `PHASE15-PRODUCTION-DEPLOYMENT-REPORT.md` confirmed zero `verification-evidence` rows in the database (every real upload attempt failed before any row committed). There is no historical data to migrate; this is a pure forward fix.
- **The `document` field on `VerificationRequests`** (the legacy Phase 10 single-file field, still `relationTo: "media"`) is unaffected — it was never part of this collection and continues to use `Media`'s existing, working, public-blob storage, exactly as designed for historical requests.
- **Regression risk to the rest of Phase 15** is low by construction: this change touches exactly one collection's `upload` config and adds one new adapter file; it does not touch `VerificationRequests`, `Appeals`, `ModerationAuditLog`, or any access-control function reviewed and approved in the prior review cycles.
- **Local development impact**: local dev's filesystem is writable, so local-disk storage never actually needed replacing there — but switching `VerificationEvidence` to a cloud adapter means local development will now also write to real (production) Vercel Blob storage during testing, the same way `Media` already does locally today. This is consistent with this project's existing pattern (dev and prod already share one database and one Blob store for `Media`) and will be disclosed in validation, not hidden.
