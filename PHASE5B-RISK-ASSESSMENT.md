# Phase 5B — Risk Assessment

## Risk matrix

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | Migration fails to correctly set `_status` on one or more of the 8 existing live records, causing a Service/Article to disappear from the public site | Low | High (direct revenue-page or SEO-page outage) | Local-API-driven backfill (not raw SQL) against an exhaustively enumerated, small (8-record) set; explicit checklist verification (`PHASE5B-MIGRATION-PLAN.md` §8) before considering migration complete; full regression test of all 8 records post-migration (`PHASE5B-VALIDATION-STRATEGY.md`) |
| R2 | Pre-existing documents with no version-table row resolve incorrectly under `draft: true` fetches (untested code path in this codebase — see Migration Plan §4) | Low–Medium | Medium (would surface as a broken preview, not a public-site issue, since public fetches don't pass `draft: true`) | Explicit validation step V-1 before sign-off; this failure mode cannot affect the public (non-preview) site because the published-only query path is unaffected by version-row presence |
| R3 | One of the 5 relationship-fan-in fields (Homepage cards, FAQ scoping, CaseStudies tags, Articles cross-refs, Services self-relation) fails to resolve a Service correctly after Services gains drafts | Low | Medium–High (broken homepage card, broken FAQ, or broken "related services" block — visible but not catastrophic) | Already-proven resolution pattern (identical to `Testimonials`, in production since Phase 5A); explicit re-verification of all 5 fan-in points as a named validation step (V-2) rather than assumed safe by analogy |
| R4 | `isPublished`/`_status` drift — a document ends up with mismatched values across the two fields, causing confusion for a future developer or editor | Low (mitigated by design) | Low (no application code reads `isPublished` after this phase, so drift is inert, not exploitable) | Deliberate decision to stop writing `isPublished` entirely rather than keep both fields live and in sync |
| R5 | SEO regression — metaTitle/metaDescription/OG/structured-data output changes for one of the 8 existing records as a side effect of the query-path switch from `isPublished` to `_status` | Low | High (organic traffic impact, slow to detect, slow to reverse) | Byte-for-byte pre/post comparison of rendered metadata and structured data for all 8 records, part of validation strategy; no field-level SEO changes are part of this phase's scope at all — only the publish-state query mechanism changes |
| R6 | Sitemap or `getPublishedServiceSlugs`/`getPublishedArticleSlugs` continues querying `isPublished` after the switch, silently omitting or including the wrong records | Low | Medium–High (SEO — incorrect sitemap) | Explicit checklist item confirming every list-query call site is migrated, not just the detail-lookup functions |
| R7 | A draft Service/Article becomes reachable by an unauthenticated user outside of preview mode (draft content leak) | Very low | High (would expose in-progress/unapproved content, e.g. unreleased pricing) | Reuses the exact `access.read` gating pattern already live in production for Pages/CaseStudies/Testimonials with zero incidents; closes rather than opens an access gap (see R9) |
| R8 | Preview link security regression via the `/api/draft` whitelist extension | Very low | High | No new security code — literally two more `else if` branches reusing the same secret/session/whitelist logic already validated live in Phase 5A (16/16 assertions passing in production) |
| R9 | *(Pre-existing, being fixed by this phase, not introduced by it)* Today, `Services`/`Articles` `access.read: anyone` means an unpublished record is technically fetchable via direct API call, bypassing the app's own filter | N/A (already true today) | Currently low real-world impact since 0 of 8 records are unpublished | Fixed as a direct consequence of adopting the Pages/CaseStudies access pattern — net security improvement, not a new risk |
| R10 | Editorial confusion during the Save Draft / Publish transition — an editor saves a change expecting it to go live immediately (old muscle memory) and it doesn't | Medium | Low–Medium (temporary confusion, not data risk — nothing is lost, the change is just not yet public) | Editor communication/training update recommended (`PHASE5B-WORKFLOW-DESIGN.md` §5) |
| R11 | Revalidation hooks fire on draft saves, causing unnecessary cache invalidation traffic | Certain (already true for Pages/CaseStudies today) | Very low (already-accepted, already-harmless behavior, documented since Phase 5) | No new mitigation needed — pre-existing, accepted behavior, not unique to this phase |

## Overall risk posture

**Moderate-low.** This phase carries genuinely more risk than Phase 5A because it is the first to retrofit drafts onto live, populated, cross-referenced collections (see `PHASE5B-ARCHITECTURE-REVIEW.md` §3, §7) — but every mitigation listed above is either a direct reuse of infrastructure already validated in production (Draft Mode, `/api/draft`, access-control pattern, relationship-resolution behavior) or a deliberately conservative sequencing choice (deferred column drop, Local-API-driven backfill, exhaustive small-record-set enumeration) specifically designed to minimize the one class of risk that IS new here: content regression on already-live data.

## Highest-priority risks to close before considering this phase safe to merge

1. **R1** (migration correctness on the 8 live records) — the single most consequential risk; addressed via the migration checklist and full regression suite.
2. **R6** (sitemap/list-query migration completeness) — silent SEO regressions are the hardest class of bug to notice quickly; addressed via an explicit call-site audit, not just detail-page testing.
3. **R3** (relationship fan-in) — the one area with the most inbound dependents of any collection touched in this project to date.
